# Поиск материалов и продолжение проектов

Пилот на Праге и Баварии. Бесплатный локальный инструмент на Python 3.10+, только стандартная библиотека. Нет установки сервиса, платного API, Notion, сетевых запросов или генерации медиа.

## Использование

Из корня полного checkout `legur/Simba`:

```bash
python3 integrations/materials/catalog.py list
python3 integrations/materials/catalog.py status Бавария
python3 integrations/materials/catalog.py resume Бавария
python3 integrations/materials/catalog.py reuse Бавария --kind animated_clip
python3 integrations/materials/catalog.py search "крупные титры" --library kadr
python3 integrations/materials/catalog.py search "Прага" --library critic
python3 integrations/materials/catalog.py check
```

Новая команда `status <проект>` сводит локальные проверки, следующий этап и ответственного. Она различает `BLOCKED` (источник изменен или ошибка записи), `NEEDS_LEO` (выбранный рабочий материал требует решения), `IN_PROGRESS` (исполнитель должен подготовить проверяемый материал), `REGISTERED_COMPLETE` (по реестру есть оба утверждения). Возвращает `checks`, `issues`, `missing`, `next_action`, `action_owner`. Не запускает генерацию, не меняет `project.json`, не проверяет удаленные MP4 и не подтверждает фактическую публикацию: `external_media_and_actual_publication=NOT_VERIFIED_BY_CATALOG`.

Для машинного результата поставьте `--json` перед командой. Для другого checkout: `--root /path/to/Simba` перед командой. На Windows вместо `python3` может использоваться `python`.

Поиск читает существующие AR-, TIA-, KADR-карточки, журналы Критика, Content Library и `campaigns/*/project.json`. Он работает с фактически имеющимися локальными файлами, без полной копии архива в контексте агента. Фраза разбивается на слова: все слова должны встречаться в документе или пути. Это текстовый поиск, не семантический подбор и не экспертное утверждение пригодности.

Результат показывает исходный статус и путь. Агент открывает полную карточку, проверяет актуальный индекс и правила выбранной роли. TEST, DRAFT, SOURCE_BLOCKED и неизвестный статус не становятся проверенными рекомендациями. Архивные/проблемные разделы `99_*` не включаются в обычную выдачу.


## Передача между этапами рилса (шаг 2, 10.11.2026)

`integrations/materials/handoff.py` — безопасный read-only адаптер, который формирует **машиночитаемый пакет для следующего существующего исполнителя**. Он использует `catalog.py`, `project.json`, правила сценария, Rafael, A2E, озвучки, музыкальных лицензий, монтажа и QA. Это не новый агент.

После подтвержденного выполнения стадии тот же `project.json` (схема v1) получает необязательную запись `stage_handoffs.<stage>`: `state`, `input_fingerprint`, `assets` (ID реально созданных артефактов), `approval_evidence`. Для сценария, раскадровки, A2E-промптов и оформления монтажа записывать `selected_option: 1..3`, `options_presented: 3`, `options_evidence`. Для A2E также `quoted_credits`, `max_credits`, `quote_evidence` и позднее `task_evidence`/task ID в фактических клипах. Для `voice_music` сохранять отдельные `text_option` и `music_option`, `texts_presented: 3`, `music_presented: 3`, утвержденный `voice_profile` и `music_license_evidence`. Финальный QA требует фактически зарегистрированные `qa_pass=true`, `qa_evidence` и `qa_report`. Отсутствующее утверждение не выдумывать.

Порядок передач: `script → Rafael → storyboard → Сценарист (A2E prompts) → A2E → голос/музыка → монтаж и выбор оформления → сборка → QA → Leo`. Каждый пакет содержит `lineage`: полный перечень предыдущих решений и ссылочных ID, при этом сами файлы не копируются и повторно не генерируются. Исходные файлы проверяются по SHA в каталоге, а `input_fingerprint` каждого последующего этапа должен равняться `expected_input_fingerprint` из предыдущего пакета. Если исходник или выбор изменился, дальнейшая передача блокируется.

```bash
python3 integrations/materials/handoff.py --json Прага
python3 integrations/materials/handoff.py --json Бавария
python3 integrations/materials/handoff.py --json --report-only all
```

**Границы:** пакет не инициирует платную генерацию, синтез, сохранение внешних файлов или публикацию, не создает GitHub issues и не меняет утверждения. Только owner-only защищенные инструменты могут запускать A2E/голос при известных параметрах и действующем разрешении. `READY_FOR_HANDOFF` означает готовность *передачи данных*, а не фактическое выполнение агентом. Реальный файл и QA подтверждаются исполнителем отдельно. Публичный репозиторий не использовать для секретов, приватного голосового ID, личных документов, клиентской переписки и персональных данных.

Старые проекты сохраняются без поддельных stage-approval: если есть рабочий MP4 и QA-отчет (как у Праги), выводится `NEEDS_LEO_REVIEW` с предупреждением «отчет записан, не проверен заново»; если `working_asset_id` отсутствует при статусе review (как у Баварии), выводится блокировка до привязки точной версии.

При обновлении проекта существующий GitHub Actions workflow автоматически собирает **диагностические JSON-пакеты** и сохраняет их как артефакт запуска. Он не вызывает внешних агентов: автоматическая выдача пакета и фактический автономный вызов разных AI-сервисов — разные уровни интеграции. Возможность запуска/подключения через агентские среды проверяется отдельно.

## Шаг 5: автоматическая очередь заданий для следующего агента (10.11.2026)

Добавлен `integrations/materials/dispatcher.py` и GitHub Actions
`.github/workflows/simba-video-stage-dispatch.yml`. Это **рабочая автоматическая
маршрутизация**: после изменения `campaigns/<id>/project.json` в `main`
GitHub Actions сверяет источники, одобрения, непрерывность `stage_handoffs`
и предыдущий receipt. Если `handoff.py` действительно разрешает следующий
этап, Actions создает **одну** GitHub Issue-задачу для нужной существующей
роли. Повторные workflow-запуски не создают дубликатов; проверяются даже закрытые
Issues. При изменении ревизии источника появится новая задача только после
нового подтвержденного write-back. Старые исторические проекты не получают
вымышленных разрешений задним числом.

Используемая цепочка: Сценарист (`script`) → Rafael (`storyboard`) →
Сценарист (`a2e_prompts`) → A2E (`a2e_clips`) → голос и музыка
(`voice_music`) → монтаж (`edit_choice`) → рендер (`render`) →
технический QA (`qa`) → утверждение Лео. В Issues передаются только
публично безопасные поля: проверенный ID проекта, имя этапа, роль, анонимный
fingerprint задачи и ссылка на существующую **публичную** карточку в GitHub.
**Не** копируются приватные медиа, их URL, коммерческие данные, секреты,
ID голоса, полный handoff или клиентская переписка: репозиторий публичный.
Все исходники и реальные ассеты исполнитель открывает по утвержденному
каноническому процессу и разрешенному доступу.

### Как работает

1. Для **нового** проекта используется обычный `project.json` с
   `stage_handoffs: {}`, заполненным проверенным `sources[]`, пустым
   `assets: []` (до получения первого сценария), `approvals.editorial` и
   `approvals.publication` = `pending`. Это единственный случай, когда
   каталог разрешает пустые assets без фальшивой заглушки.
2. При merge/push в `main` workflow проверяет **только изменившиеся**
   `campaigns/*/project.json`. Если `handoff.state=NEEDS_FIRST_STAGE`,
   создается задача для Сценариста (3 полных варианта и выбор Лео).
3. Исполнитель предъявляет реальные варианты. Только после выбора Лео
   результат и его свидетельство записываются в **тот же**
   `stage_handoffs.<stage>` с допустимыми ID ассетов и отпечатком входа.
   Следующий push автоматически ставит задачу следующей роли.
4. При `BLOCKED`, просроченном SHA, неполной истории решений,
   `APPROVED_UNPUBLISHED` и закрытом проекте **не создается задача**.
   Выбор из трех вариантов, лимит A2E, утвержденный голос, лицензию музыки и
   техQA продолжает проверять существующий `handoff.py`; диспетчер не
   обходит эти gates.
5. Только `push main` получает permission `issues: write`; PR запускает
   только тесты. Автодиспетчер не имеет ключей A2E, Gemini, Drive и не
   запускает ни одного provider API. Прошедший рендер/QA не появляется
   без фактического выхода исполнителя.

### Запуск и ограничения

```bash
python3 integrations/materials/dispatcher.py --all
python3 -m unittest discover -s integrations/materials -p test_dispatcher.py -v
```

`--all` — только read-only предпросмотр, **никогда** не постит Issues.
Реальный `--execute --before <git-sha> --after <git-sha>` может исполняться
только из доверенного `push main` в GitHub Actions с `GITHUB_TOKEN`.
Workflow сам вычисляет измененные карточки и серийно обрабатывает задачи.

**Честная граница Step 5:** рабочая автоматизация **маршрутизации и создания
следующей GitHub Issue** уже реализована. Это **не** автономный запуск
Сценариста/Рафаэля в ChatGPT и не исполнение приватных A2E/TTS/renderer
по Issue без привязанных runtime и авторизации. Чтобы агенты действительно
работали без открытия Issues человеком, нужна отдельная безопасная
интеграция исполнительных сервисов/разрешенных API. Не называть задачи
`TASK_ISSUE_CREATED_NOT_EXECUTED` готовым сценарием, кадрами или роликом.
Коммерческий фактчек в зоне ответственности Киностудии отсутствует.

## Шаг 5B. Первый настоящий AI-исполнитель: Сценарист (10.11.2026)

Сразу после автоматического создания Issue **первого** этапа `script`,
тот же доверенный GitHub Actions runner теперь может вызвать **реальную
локальную языковую модель Qwen3:1.7b (Ollama, Apache-2.0)**, подготовить
три полных **черновых** варианта речи на русском и положить их в приватную
папку Google Drive **Simba Private AI Drafts**:
https://drive.google.com/drive/folders/1GMoSVogs0SKuTAXCdMVcG-U7bTn-IuCt.
Эта папка проверена как `shared=false`, доступ только владельцу.

Триггер строго ограничен результатом `dispatcher.py`:
`TASK_ISSUE_CREATED_NOT_EXECUTED`, `stage=script`, один новый проект,
`handoff=NEEDS_FIRST_STAGE`, `stage_handoffs={}`,
`approvals.editorial=pending`; автор запуска `legur`, `push main`.
Модель запускается **локально на стандартном Github-hosted runner
публичного репозитория**, без платных API и без передачи промпта облачной
модели. В качестве источника — только одобренный `APPROVED_TEXT` из
`03_CONTENT_LIBRARY`, с предварительной сверкой точного SHA256. Внешние
ссылки, приватные голосовые ID и содержимое черновиков не отправляются
в публичные Issues/логи/артефакты GitHub.

**Качество черновиков:** после первого живого smoke на маленькой 1.7B-модели обнаружены неполные/списочные тексты; модель увеличена до 4B, добавлен обязательный структурный QA речи (объем, предложения, слова, запрет нумерации и мета-ответа) с максимум одним бесплатным повтором. Это проверка структуры, не обещание литературного качества.\n\n**Состояние выхода**: `DRAFT_OPTIONS_NEED_LEO`. Черновые материалы
пишутся только в закрытый Drive, без изменения `stage_handoffs`, без
автоматического выбора или `editorial=approved`. Файлы имеют имя
`Simba_<project-id>_SCENARIST_3_DRAFTS_<source-revision>.md`,
по нему повторный запуск проверяет приватный архив *до* обращения
к модели. Проверка чисел/телефонов в генерируемом тексте — контроль переноса
из утвержденного источника, не фактчек предложения.

Для запуска по содержанию новых проектов:
- `python3 integrations/materials/auto_script.py --dispatch-report ... --private-folder ...`
  без `--execute` только показывает безопасный план.
- `--execute` работает только из доверенного `push main` и требует уже
  сохраненных в Actions Secret пользовательских учетных данных Google Drive.
  При недоступности локальной модели/приватного Drive процесс падает
  **без платного fallback и без заявления, что сценарии готовы**.
- Код: `integrations/materials/auto_script.py`; тесты:
  `python3 -m unittest discover -s integrations/materials -p test_auto_script.py -v`.

**Границы:** это **один действительно исполняемый AI-этап** (`script`),
а не автоматический Рафаэль, A2E или монтаж. Последующие роли пока получают
проверенные Issue-задания, а не запускаются автономно. Три варианта
раскадровки требуют реальных изображений/предпросмотра; переименовывать
текстовые предложения в готовые изображения нельзя. A2E/TTS имеют
отдельные границы стоимости и разрешений. Финальный монтаж, голос,
субтитры, QA и публикация не запускаются этим кодом.

## Файлы в закрытой ChatGPT Library (10.11.2026)

Если готовый MP4 находится в **закрытой ChatGPT Library**, а прямой публичный HTTPS-адрес отсутствует, его можно зарегистрировать в `project.json` как asset со следующими полями: `storage: "chatgpt_library"`, `library_path` (полный путь внутри Library), `library_file_id` (реальный стабильный ID из read-back), `recorded_sha256`, `evidence`, `state: "available"`. `url` **не требуется и не подменяется** фиктивной страницей загрузки. `catalog.py check` проверяет форму ID и пути, но **не читает удаленный MP4**; фактический SHA-256 необходимо сверять отдельным инструментом до объявления результата проверенным. CLI `reuse` печатает путь в Library, а не выдуманную ссылку.

Решение Лео «подходит как финальный» относится к названному файлу и его SHA. В реестре `approved_asset_id` указывает именно на этот asset, `approvals.editorial` фиксирует `approved` и точное текстовое основание. `approvals.publication` остается `pending` до отдельной команды. Старые проекты и публичные HTTPS-активы продолжают работать без изменений.

## Завершение публикации по сообщению Leo

Для рабочего видеопроекта сообщение Leo «ролик опубликован» означает **завершение производственной задачи**, если конкретный MP4 уже редакционно утвержден. Фиксировать `approvals.publication=approved`, `publication_evidence` с точной цитатой и `publication_record.status=reported_by_leo_not_verified` (не притворяться, что страницу поста проверили). `stage=PUBLICATION_REPORTED_BY_LEO__CLOSED`, `missing=[]`. `catalog.py status` возвращает `PUBLICATION_REPORTED_COMPLETE`, а `handoff.py` — пакет со стадией `closed`; повторная публикация не выполняется. Указание URL поста **не является обязательным** для закрытия производства. Проверка актуальности фактов оффера не относится к задачам Киностудии и не добавляется в `missing` / `next_action`.

## Как продолжать проект

1. Обновить checkout из `main`, либо прочитать актуальные файлы через GitHub-инструменты.
2. Найти проект в [реестре](../../campaigns/README.md), открыть его `project.json` и перечисленные `sources`.
3. Выполнить `resume`. Команда сверяет SHA-256 текстов источников. `STALE_SOURCE` означает: сначала прочитать изменившийся источник и согласовать состояние карточки; прежний `next_action` не исполнять автоматически. Возвращается exit code 2.
4. Сверить последнюю текущую правку Лео: сообщения другого чата могут быть новее файлов. Контроль SHA обнаруживает изменения только локально прочитанных файлов, не чужую переписку или замену медиа на Drive.
5. Через `reuse` найти сохраненные исходники; открыть реальный файл и проверить его перед использованием. `recorded_size_bytes`, `recorded_sha256`, `evidence` — сведения из исходной сессии, а не новая проверка внешнего файла.
6. Выполнить только требуемую роль и стадию по действующему workflow. Каталог не выдает разрешения на синтез/анимацию, платный повтор или публикацию.
7. После стадии обновить существующую каноническую сессию, затем тот же `project.json`: новые ссылки, состояние, следующий шаг, отсутствующее, выбранную рабочую версию. Пересчитать `sources[].sha256` по точным байтам актуального файла. Записать оба изменения одним коммитом и проверить read-back.

Готовая контрольная команда для хеша:

```bash
python3 -c "import hashlib,pathlib; print(hashlib.sha256(pathlib.Path('путь-к-источнику').read_bytes()).hexdigest())"
```

Не переписывать хеш, чтобы скрыть неизвестное изменение. Сначала сверить смысл новой редакции. Не обновлять карточку только по названию `final` или дате файла.

## Данные проекта

`project.json` — компактный указатель состояния, а не копия сценария или правил агента. Одна запись на постоянный `id`. Переиспользуемые знания остаются в своих библиотеках с исходными AR/TIA/KADR-ID.

- `sources`: основные тексты и отпечатки прочитанных редакций.
- `stage`, `next_action`, `missing`: место продолжения работы.
- `assets`: только реально найденные стабильные ссылки; сохраненные размеры/хеши явно помечены `recorded_*`.
- `working_asset_id`: версия для текущей работы, не утвержденный финал.
- `approved_asset_id`: конкретный утвержденный файл либо `null`.
- `approvals`: отдельные editorial/publication; `approved` требует отдельного evidence.
- `references`: исходные карточки и характер связи. Не объявлять карточку примененной только потому, что она найдена.
- `latest_user_request`: конкретная более поздняя правка, когда источник еще не содержит ее исполнения.

Повторный поиск и чтение не меняют файлы. Автоматического обновления из других чатов нет. Инструмент не меняет права Google Drive и не считает сохранение файла подтверждением публикации.

## Проверка

```bash
python3 -m unittest discover -s integrations/materials -p test_catalog.py -v
python3 integrations/materials/catalog.py check
```

Проверяются устаревание/отсутствие источников, неоднозначный проект, статусы, дубли ID, выбранные файлы, доказательство утверждения, временные URL и выход пути за checkout. Доступность и содержимое внешних файлов проверяются выбранным исполнителем отдельно.
