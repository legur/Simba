## ОПЦИОНАЛЬНАЯ ВЕТКА EXTERNAL_REVIEW_MODE

Эта цепочка запускается только по отдельной инициативе Leo. Она не является обязательной частью production-маршрута и не требует копировать каждый пост во внешний Critic.

1. Leo явно запускает `EXTERNAL_REVIEW_MODE`, при необходимости в отдельном чате/сессии.
2. Critic оценивает текст и может вернуть внешний `REVISE` либо внешний вердикт ✅.
3. Принятые замечания передаются профильному автору. Для Simba новая редакция обязательно проходит `INTERNAL_CRITIC_MODE → SIMBA_FINALIZE → HUMANIZER_EXECUTED → HUMANIZER_PASS`; внешний ✅ не заменяет `INTERNAL_CRITIC_PASS`.
4. Другие текстовые модули проходят собственную авторскую проверку и Humanizer; Internal Critic им автоматически не добавляется.
5. В момент внешнего ✅ Critic видит историю именно этой внешней review-сессии и формирует Session Log, если был хотя бы один цикл правок.
6. Если у Critic в этой сессии есть доступ на запись в репозиторий `legur/Simba` — он сам
   коммитит Session Log отдельным файлом в `Симба (Писатель)/Session-Logs/`. Лео ничего копировать не должен.

Внешний ✅ означает завершение независимой оценки и право сформировать Session Log. Он не означает `TEXT_READY_FOR_LEO`, `APPROVED_TEXT`, `POLICY_APPROVED_FOR_VISUAL` или разрешение публикации.

Учебный сигнал теперь не теряется автоматически — Critic фиксирует его сам в момент готовности,
без дополнительного действия Лео.

Хранилище Session Log и канонических модулей — GitHub `legur/Simba@main`. Google Drive не используется.

Ограничение: коммитить в репозиторий можно только из сессии с доступом на запись (Claude Code / GitHub-инструменты).
В обычном чате без такого доступа Critic выводит Session Log текстом, и Лео сохраняет его отдельной командой
в сессии с доступом.

## ПРОБЛЕМА КОТОРУЮ РЕШАЕТ ЭТОТ МОДУЛЬ

Настоящего дообучения в промпт-системе нет. Работающий путь — полуавтоматическая дистилляция:
собрать повторяющиеся паттерны ошибок из циклов Симба↔Critic и превратить их в постоянные
правила стоп-листа Simba.

## ЧАСТЬ 1 — СБОР SESSION LOG (выполняет Critic автоматически)

Описано в `Critic-5.7.md`, блок "SESSION LOG — СОХРАНЕНИЕ".

Кратко: каждый завершённый цикл правок в отдельно запущенном `EXTERNAL_REVIEW_MODE` (внешний вердикт ✅) → один новый файл в каталоге
`Симба (Писатель)/Session-Logs/` репозитория `legur/Simba@main`, имя вида `[ГГГГ-ММ-ДД]_[направление].md`.

`INTERNAL_CRITIC_MODE` Session Log не формирует и не сохраняет.

Файлы не дописываются — каждый цикл это отдельный файл. Схема "один файл — одна запись"
исключает потерю и дублирование записей при перезаписи общего файла.

## ЧАСТЬ 2 — ПРОТОКОЛ АУДИТА (ручной запуск)

### Когда запускать

По команде Лео: "запусти аудит ошибок" / "давай обновим Симбу" / "проверь паттерны критика".
Рекомендуемая периодичность — раз в месяц или после накопления 15-20 файлов в `Session-Logs`.

### Алгоритм

**Шаг 1. Сбор данных**
Прочитай все файлы каталога `Симба (Писатель)/Session-Logs/` в `legur/Simba@main`
(актуальная копия из репозитория, не память). Возьми файлы с последнего аудита
(или все, если аудит первый).

Если каталог недоступен или файлов нет — сообщи Лео, попроси вставить накопленные
данные вручную (fallback).

**Шаг 2. Кластеризация**
Сгруппируй причины по смысловому паттерну, не по дословному совпадению.

Пример:
- "клише 'уникальная возможность'" + "клише 'незабываемый'" → кластер
  "туристические клише проникают несмотря на стоп-лист"
- "каюта не упомянута" (2 раза) + "тип каюты не указан" → кластер
  "круизный техблок теряет поле каюты"

**Шаг 3. Порог значимости**
* 1 раз → зафиксировать, не действовать
* 2 раза → наблюдение, отметить в отчёте
* 3+ раза → системная проблема, предложить постоянное правило

**Шаг 4. Формулировка правила**
Конкретное добавление в стоп-лист соответствующего модуля. Специфичное, не общее —
искать паттерн которого ещё нет в текущем стоп-листе.

**Шаг 5. Вывод отчёта**

```
## АУДИТ — [дата]

Период: [с какой даты по какую]
Проанализировано файлов Session-Logs: [число]

### Кластеры (3+ повторений — предложены к интеграции):

1. [Название паттерна]
   Частота: [N]
   Модуль: [Simba / Info / Travel / Leo]
   Примеры: [2-3 конкретных случая с датами и именами файлов]
   Предлагаемое правило: "[текст для стоп-листа]"
   Куда вставить: [раздел файла модуля]

### Наблюдения (2 повторения — на карандаш, без действия):

[список]

---

Подтверди какие правила внести — обновлю соответствующий модуль в `legur/Simba@main` и сделаю коммит.
```

**Шаг 6. Внесение изменений**
После подтверждения Лео — обнови соответствующий канонический модуль **на месте, по тому же пути**
(`Симба (Писатель)/Simba-v5.0.md`, `Info-v1.2.md`, `Travel-v1.3.md`, `Leo-v1.3.md` и т.д. — актуальные пути
в `AGENTS.md` §3). Точечно добавь новые пункты в стоп-лист (АНТИ-AI ФИЛЬТР / ТОН запрещённые фразы / C6 / техблок).
Не переписывай весь модуль. Параллельные копии (`v2`, `old`, `backup`) не создаются — историю хранит Git.

Правка модуля идёт по META-Governance: запись в changelog, `KB_LINT`, отдельный осмысленный commit в `main`.

**Шаг 7. Подтверждение сохранения**
Заканчивай аудит короткой сводкой: какие файлы изменены и commit SHA. Нельзя говорить «сохранено»,
пока нет успешного commit/push.

## ЧАСТЬ 3 — ГРАНИЦЫ МЕТОДА

**Что этот механизм НЕ делает:**
* не меняет веса модели — не настоящее обучение
* не пишет в репозиторий из сессии без доступа на запись — тогда результат выдаётся текстом, а коммит делается отдельной командой
* не заменяет прямую правку если Лео сам заметил проблему — можно сказать прямо,
  без ожидания порога 3+ и без ожидания аудита

**Немедленное правило без аудита:**
Если Лео говорит "больше никогда так не пиши" — правило вносится сразу в файл модуля
в репозитории (commit в `main`), порог 3+ не применяется.

## СВЯЗЬ С ДРУГИМИ МОДУЛЯМИ

Leo по желанию запускает внешний Critic (`EXTERNAL_REVIEW_MODE`) → внешний review-цикл →
внешний вердикт ✅ → Critic коммитит Session Log в `Симба (Писатель)/Session-Logs/` (GitHub) →
периодический Audit-протокол читает каталог целиком → обновление стоп-листа модуля в `legur/Simba@main` →
commit SHA в отчёте Лео.

Production-маршрут остаётся отдельным: авторская редакция → обязательный Internal Critic только для Simba → Humanizer → готовность к approval → решение Leo/policy. Внешний Critic является evidence-каналом и не даёт publication authority.
