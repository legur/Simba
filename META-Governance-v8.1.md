## ИСТОЧНИК ИСТИНЫ — GITHUB

С 02.10.2026 единственный канонический источник истины системы — приватный репозиторий **`legur/Simba`**, ветка **`main`**.

### Обязательный процесс системной правки

1. Прочитать актуальный файл из `legur/Simba@main`; не работать по памяти или старой копии.
2. Выполнить META/KB preflight для затрагиваемого компонента.
3. Обновлять канонический файл **по тому же пути**. Не создавать параллельные `v2`, `old`, `backup`, `final-final`.
4. Сохранить изменение отдельным осмысленным Git-коммитом.
5. Перечитать изменённые файлы и проверить дерево/ссылки после записи.
6. Если изменение затрагивает Router, META, `00_CORE`, workflow или KB-зависимости — выполнить `KB_LINT.md`.
7. Для production write-back (APPROVED, PUBLISHED, CORRECTIONS, DECISIONS) писать сразу в соответствующий каталог этого репозитория.

### Google Drive после миграции

Папка **`New Simba`** на Google Drive является **архивом/источником миграции**, а не runtime-источником истины.

- штатное чтение и запись системы идут через GitHub;
- двусторонней синхронизации GitHub ↔ Google Drive нет;
- изменение файла на Drive само по себе не меняет Simba;
- Drive читается только по явной задаче Leo: сверка архива, восстановление или повторная миграция конкретного материала;
- при конфликте GitHub `main` имеет приоритет, если Leo явно не распорядился иначе.

### Runtime adapter

`AGENTS.md` в корне репозитория определяет точку входа и физические пути модулей для Codex/агентной среды. Он не заменяет Router, META или профильные правила, а обеспечивает их корректную загрузку из GitHub.

### Runtime invariants: Source → Executor → Provenance


После решения Leo 08.09.2026 каноническими считаются следующие hard gates:


1. **SOURCE RESOLUTION:** email/source нельзя классифицировать как неполный до проверки body, HTML/raw MIME, attachments, inline creatives и доступной web/campaign version. Неразрешимый технический источник = `SOURCE_BLOCKED`.
2. **DUAL VALUE:** для supplier-email `COMMERCIAL_SCORE` и `NEWS_SCORE` независимы. Цена не является gate для `NEWS_HIGH`.
3. **EXECUTION GATE:** выбранный профильный модуль обязан фактически загрузить актуальные правила и выполнить результат. Router/Маркетолог не имеют права закрывать работу вместо News/Simba/Info/Travel/Leo/Rafael. Нарушение = `BLOCKED_EXECUTOR_NOT_RUN`.
4. **RAFAEL/RENDERER SEPARATION:** Rafael владеет визуальной концепцией и production-prompt; image generator только рендерит. Prompt, придуманный оркестратором напрямую, не считается исполнением Rafael.
5. **PROVENANCE:** каждый production-result сохраняет источник, классификацию, стратегический слой, текстового исполнителя, визуального исполнителя, renderer, execution states и status.
6. **AUTOMATION_CONTINUOUS_MODE:** заранее разрешенная Leo автоматизация может заменить интерактивное одобрение текста на `POLICY_APPROVED_FOR_VISUAL` только для перехода к Rafael. Автопубликация от этого не разрешается.


Эти правила должны быть синхронизированы в Router, AI-Маркетологе и `SIMBA KNOWLEDGE BASE/00_CORE + 06_AGENT_WORKFLOWS`.


### Зависимость AI-Маркетолог → исполнительные модули


AI-Маркетолог не заменяет существующие модули и не выполняет их творческую работу, но как `PROCESS_OWNER` сопровождает маркетинговый workflow до предусмотренного конечного state; его ответственность не заканчивается в момент запуска генерации.


- Его зона ответственности: оценка продукта, определение объекта рекламы (один продукт или вся подборка), аудитория, Job to Be Done, канал, бизнес-цель, воронка, CRO, SEO/AEO и рекламные гипотезы.
- Он передаёт исполнительному модулю задание по единому контракту: предварительная загрузка правил, тип результата, объект рекламы, подтверждённые данные, аудитория и канал, бизнес-цель, маркетинговые рекомендации, запреты и контракт результата.
- Для Simba он рекомендует приоритетный angle, заголовок, hook, структуру аргументации, ключевой аргумент, авторские формулировки и CTA. Эти элементы не являются готовым постом и могут быть адаптированы Simba по собственным правилам.
- Для Rafael визуальный промпт, композиция, стиль, палитра и текст постера пока не передаются: визуальный контракт будет согласован отдельно.
- Перед началом исполнения каждый выбранный модуль обязан полностью перечитать собственный актуальный файл и все указанные в нём обязательные зависимости. Если правила недоступны, генерация не начинается.
- Simba, Info, Travel, Leo и News сохраняют собственные правила голоса, структуры, TIA и финальной проверки. Исключение: каждый результат Simba до выдачи Leo проходит обязательный скрытый `INTERNAL_CRITIC_MODE`; для Info/Travel/Leo/News этот gate автоматически не вводится. Внешний review Critic остается отдельным вызовом по инициативе Leo.
- Rafael и Люмьер сохраняют собственные визуальные и технические процессы; маркетинговый бриф задаёт задачу, но не формат реализации.
- Перед каждым вызовом Rafael Router и AI-Маркетолог обязаны потребовать, чтобы Rafael сначала полностью перечитал актуальные правила и все обязательные зависимости, а затем выполнил предусмотренное ими количество вариантов, проверки и формат выдачи. Сокращённый результат не принимается как финальный.
- Humanizer применяется после генерации текста и не имеет права удалить ключевую ценность, proof или CTA из утверждённого брифа.
- Feedback Learning применяется только когда итогом является Facebook-пост, даже если запрос был сначала обработан AI-Маркетологом.
- Фактологическая верификация обязательна до verdict и повторяется исполнительным модулем для изменяемых деталей, если между этапами появилась новая информация.


Маршрут по умолчанию:


**сырой продукт или подборка → AI-Маркетолог/PROCESS_OWNER → бизнес-задание + маркетинговая гипотеза → профильный модуль → [для Simba: Internal Critic repair loop] → финальный результат Leo → продолжение workflow до конечного state**


### HARD DEFAULT для source-only input
Если Leo присылает содержательный внешний источник без отдельной команды (ссылка, статья, письмо, PDF, изображение/скрин, внешний текст), это автоматически считается `NEW_SOURCE`.


Обязательный маршрут: `SOURCE_ONLY_INPUT → NEW_SOURCE → ROUTER_CORE_PREFLIGHT → ROUTER_TASK_CLASSIFIED → MODULE_KB_PREFLIGHT → PROFILE_MODULE → RESULT_TO_LEO`.


Не задавать вопрос «что сделать с материалом?», если тип задачи можно определить по содержанию. Не создавать пост напрямую в обход Router. Явное текущее указание Leo имеет приоритет. Внешний Critic/пользовательский review автоматически не запускается; однако результат Simba обязательно проходит скрытый `INTERNAL_CRITIC_MODE` до выдачи Leo.


Для компактной подборки горящих туров с близкими вылетами и подтверждённым ограничением мест вся подборка может быть единым рекламным продуктом. В этом случае Маркетолог не выбирает один тур-победитель, а ставит задачу рекламировать все позиции; оценка влияет только на порядок показа и контроль качества данных.


### AI-Маркетолог как PROCESS_OWNER
AI-Маркетолог не подменяет Simba, Critic, Rafael и другие модули, но остается владельцем маркетингового workflow от нормализации источника до предусмотренного конечного state. Handoff другому модулю не считается завершением задачи.


Для Simba обязательна последовательность: `SIMBA_DRAFT_READY → INTERNAL_CRITIC_MODE → [REVISE → SIMBA_REPAIR]* → INTERNAL_CRITIC_PASS → SIMBA_FINALIZE → TEXT_READY_FOR_LEO`. После одобрения Leo финального текста запускается установленный Rafael trigger без дополнительного вопроса.


Если Leo приносит замечания внешнего критика, это evidence текущей доработки: Маркетолог фильтрует их на применимость, передает Simba, и новая редакция снова проходит Internal Critic.




Если пользователь уже выбрал продукт и просит только конкретный готовый материал, Router минует AI-Маркетолога и вызывает профильный модуль напрямую.


### HERO IDENTITY INVARIANT — личные и экспертные посты
Для визуального этапа действует постоянное решение Leo:
- `TEXT_EXECUTOR=Leo` / личный пост → главный визуальный герой Leo; Simba absent по умолчанию;
- `TEXT_EXECUTOR=Info` / экспертный или справочный пост → главный визуальный герой Leo; Simba absent по умолчанию;
- остальные типы сохраняют Routing / Template Lock Rafael.


Это правило меняет только identity героя и не отменяет остальные обязательные этапы Rafael.


### Зависимость Rafael → Archivarius + YouMind AI Image Prompts


Начиная с runtime patch 05.09.2026, у визуального процесса два постоянных reference-source слоя. Попытка поиска в обоих обязательна, но техническая недоступность внешней библиотеки не является stop-condition.


**Archivarius / `01_Изображения`** остаётся локальной курируемой библиотекой Simba / Bon Tours:
- Rafael обязан выполнить поиск активных prompt-карточек до создания концепций;
- при отсутствии точной карточки используются ближайшие карточки или их комбинация;
- локальная библиотека имеет приоритет над YouMind при равном качестве решения.


**YouMind AI Image Prompts** — внешний живой источник `https://github.com/YouMind-OpenLab/ai-image-prompts-skill`:
- перед каждым поиском Rafael читает актуальный `references/manifest.json`, не использует захардкоженный список категорий;
- ищет только в релевантных category JSON и не загружает большие файлы целиком;
- выбирает максимум 3 prompt-шаблона на запрос;
- использует только записи с непустым `sourceMedia`, а первую sample image — как внутренний визуальный референс;
- записи `needReferenceImages=true` пропускаются, если Лео не дал подходящее reference image;
- если есть локально установленный mirror, он допустим только после проверки свежести по правилам репозитория; устаревшая более чем на 24 часа копия сначала синхронизируется.


**Общие правила двух библиотек:**
- перед концепциями Rafael обязан попытаться выполнить оба поиска;
- Archivarius: сначала trusted, затем остальные релевантные `active` visual cards вне blocklist;
- правила Rafael, Template Lock, факты оффера, Routing и Styles имеют приоритет над обеими библиотеками;
- prompt-механика адаптируется, а не копируется механически;
- если недоступна одна библиотека, Rafael продолжает со второй; если недоступны обе, продолжает по Visual Rules с `REFERENCE_LIBRARIES_UNAVAILABLE`;
- после генерации Leo видит названия реально использованных карточек/шаблонов; полный prompt/JSON/sample не показывается без запроса;
- тот же `REFERENCE_TRACE` сохраняется по вариантам 1–5 в visual-session / публикационном пакете.


Это изменение затрагивает Rafael, его Architecture, Router и META, но не меняет правила текстовых модулей Simba, Info, Travel, Leo, News и Humanizer. AI-Маркетолог не требует правки: его существующий preflight уже требует перечитать все обязательные зависимости Rafael.

## ТИПЫ ИЗМЕНЕНИЙ


Перед началом работы классифицируй запрос. Это определяет объём процесса.


**1. Точечная правка** — исправление формулировки, правила, примера внутри одного модуля.
Не меняет структуру файла, не создаёт новых зависимостей между модулями.


**2. Структурное изменение** — новый блок правил, новый шаг в алгоритме, изменение
логики выбора (например, критериев routing). Может задеть смежные модули (Critic, Humanizer).


**3. Архитектурный рефакторинг** — разбивка файла на несколько, слияние модулей,
изменение способа взаимодействия (как было с Rafael v3.0 → 4 файла).


**4. Новый модуль** — создание с нуля. Полный алгоритм — см. раздел
АЛГОРИТМ СОЗДАНИЯ НОВОГО МОДУЛЯ ниже. Общий процесс (Шаги 1-7 из ОБЯЗАТЕЛЬНОГО ПРОЦЕССА)
применяется поверх него на этапе версионирования и доставки.


Тип изменения вслух не объявлять пользователю, если не спросили — но держать в голове,
потому что от него зависит, сколько файлов трогать и что проверять на пересечениях.


Прецедент Типа 2: добавление блока RAFAEL — НЕ ТЕКСТОВЫЙ МОДУЛЬ в ROUTER (v1.1 → v2.0) —
новый шаг маршрутизации (перенаправление в исполнительную среду до выбора текстового
модуля), не затрагивает сами модули Simba/Info/Travel/Leo/News, но меняет routing-логику
роутера целиком → MAJOR, не MINOR.

## АЛГОРИТМ СОЗДАНИЯ НОВОГО МОДУЛЯ


Разворачивается, когда Тип изменения = "Новый модуль". Заменяет собой Шаги 1-3
общего процесса (диагностика / чтение / предложение) — здесь они детализированы под
проектирование с нуля. Шаги 4-7 общего процесса (правка / проверка / версия / доставка)
идут после, без изменений.


**Шаг 0. Проверка необходимости**
Сверить с ROUTER: действительно ли это новый модуль, а не вариант существующего?
Признак ложного нового модуля — задача решается новым Вариантом внутри Simba/Info/Travel/Leo
(так уже был закрыт кейс Leona → Simba В4). Создавать новый файл только если у контента
принципиально другая цель, аудитория или голос, которые не ложатся ни в один Вариант
существующего модуля.


**Шаг 1. Сбор вводных**
Не начинать проектирование, пока не закрыты все пункты:
- Цель модуля — что должно произойти после прочтения (написать в личку / подписаться /
  сохранить / отреагировать / что-то ещё). Один модуль — одна доминирующая цель.
- Голос — от чьего лица: Simba-бренд (безличный, коммерческий) или Лео лично (первое лицо,
  мужской род, как в Leo/Travel/Info).
- Аудитория — дефолт 45+, женщины 80% — или явное отклонение с обоснованием.
- Триггеры активации — конкретные слова/фразы для явного вызова (пойдут в ROUTER,
  таблица "Сигнал → Модуль") + признаки для авто-детекта по содержанию.
- Формат вывода — сколько вариантов (3 как у большинства, 4 если нужен мягкий доп.вариант),
  нужен ли TIA-блок, нужны ли контакты/CTA.
- Пересечение с продажей — если да, нужен техблок и контакты; если нет (как Leo/Travel) —
  контакты запрещены явно, не по умолчанию.


Если хотя бы один пункт не закрыт — не переходить к Шагу 2. Задать точечный вопрос.


**Шаг 2. Границы с существующими модулями**
Прописать явное разграничение по образцу "Leo vs Travel: Travel — герой место, Leo — герой Лео"
из ROUTER. Разграничение должно быть проверяемым — не "модуль про личное", а конкретный
признак, по которому Router сможет однозначно направить запрос. Без этого шага модуль
провоцирует ошибки роутинга при первом же пограничном кейсе.


**Шаг 3. Скелет по стандартной структуре**
Все активные модули (Simba, Info, Travel, Leo, News) держат один и тот же каркас блоков.
Заполнить каждый под новый модуль — не оставлять формулировки общими:


1. Идентичность — кто говорит, от чьего лица, тон, что запрещено
2. Аудитория — если отличается от дефолта, обосновать чем
3. Минимум данных для старта — обязательные поля + блокирующие пробелы (стоп) +
   неблокирующие пробелы (пропустить молча)
4. Алгоритм работы — пронумерованные шаги: проверка данных → анализ материала →
   выбор TIA-карточек → генерация N вариантов → анти-AI фильтр → внутренняя финальная проверка модуля → вывод
5. Логика вариантов — цель, стиль и структура для каждого из N вариантов отдельно
6. Структура поста — хук / тело / (человеческое суждение или финальный вопрос,
   в зависимости от цели модуля) / техблок или его отсутствие / CTA и контакты или их запрет
7. Анти-AI фильтр — стоп-лист специфичный для голоса модуля, не копия чужого
8. Финальная проверка — чеклист по разделам (структура / голос / факты или engagement / оформление)
9. Эталон голоса — минимум один готовый пример, который сам проходит чеклист из блока 8
10. Входные данные — что даёт пользователь, что возвращает модуль, строка следующего шага


Прецедент отклонения от каркаса: News-v1.md заменил TIA-выбор по вариантам на фиксированную
структуру (2 варианта без авто-выбора TIA-карточек под каждый) — оправдано тем, что цель
News (полнота факта) конфликтует с логикой TIA (приёмы усиления одной мысли). Отклонение от
стандартного каркаса допустимо, если сама цель модуля противоречит шаблону — не по умолчанию.


**Шаг 4. Совместимость с Critic**
Обязательный `INTERNAL_CRITIC_MODE` является production-gate **только для Simba**. При изменении Simba или критериев Critic необходимо проверить совместимость repair-loop и отсутствие циклического deadlock.


Для новых модулей Internal Critic не распространяется автоматически: его подключение требует отдельного решения Leo. `EXTERNAL_REVIEW_MODE` остается независимым пользовательским инструментом и не блокирует production-релиз нового модуля.


**Шаг 5. Обновление ROUTER**
Обязательно, не опционально — модуль без записи в ROUTER недостижим для пользователя:
- строка в таблице МОДУЛИ СИСТЕМЫ (файл, статус)
- строка в таблице "Сигнал → Модуль" (явные триггеры из Шага 1)

- граница с соседними модулями (результат Шага 2 этого алгоритма)

## ОБЯЗАТЕЛЬНЫЙ ПРОЦЕСС ДЛЯ ЛЮБОГО ИЗМЕНЕНИЯ


**Шаг 1. Диагностика причины, не симптома**
Не чинить формулировку, если проблема — в отсутствующем шаге алгоритма или пути роутинга.
Спросить себя: это баг конкретной строки, или дыра в архитектуре, которая проявилась здесь?


**Шаг 2. Проверка по факту, не по памяти**
Источник — Drive напрямую через MCP-инструменты `Google Drive:*`, не память о прошлых
сессиях и не предположение о версии (см. раздел ИСТОЧНИК ИСТИНЫ выше). Проверить номер
версии в имени файла на Drive — он может быть выше того, что видно в Project knowledge
или помнится с прошлых сессий. Если MCP Drive недоступен в этой сессии — fallback на
Project knowledge / ручную загрузку, тоже описанный в разделе ИСТОЧНИК ИСТИНЫ.


**Шаг 3. Предложение до исполнения**
Сформулировать: что меняется, зачем, что заденет (другие модули, Critic, Humanizer, TIA-логику).
Дождаться подтверждения. Исключение — прямой явный приказ с описанием точной правки.


**Шаг 4. Точечное применение**
Если работа идёт напрямую с Drive (основной путь) — Drive не поддерживает надёжную
перезапись файла на месте: собрать полный текст с точечным изменением локально,
затем `Google Drive:create_file` как новую версию (см. ИСТОЧНИК ИСТИНЫ, шаг 4 процесса
там же, и раздел ВЕРСИОНИРОВАНИЕ). Если работа идёт в fallback-режиме на локальной
копии — `str_replace` с точным совпадением, не переписывать файл целиком, если задача —
локальная правка. Переписывание с нуля оправдано только при архитектурном рефакторинге
(Тип 3), в обоих режимах.


**Шаг 5. Проверка целостности**
`grep` на затронутые термины, `wc -l` на объём, сверка что структура файла (заголовки,
нумерация шагов) не сломалась.


**Шаг 6. Версия и changelog**
Обновить номер версии по правилам ниже. Добавить запись в changelog (Architecture.md
для Rafael; для остальных модулей — changelog можно вести в первых строках файла
или отдельным CHANGELOG.md, если правок становится много).


**Шаг 7. Доставка**
Основной путь: файл уже на Drive после `create_file` — в ответе есть ссылка, её и сообщить
Лео. Копия в `/mnt/user-data/outputs/` + `present_files` — дополнительно, если Лео хочет
увидеть файл сразу в чате, не обязательный шаг. Fallback-режим (MCP недоступен): как раньше —
копия в outputs, `present_files`, напоминание что на Drive/в Project knowledge файл заливает
Лео сам. Без лишнего пересказа того, что уже было проговорено на шаге предложения.

## ВЕРСИОНИРОВАНИЕ


Формат: `MAJOR.MINOR`


**MINOR (+0.1)** — точечная правка, не меняющая структуру или логику взаимодействия модулей.
Пример: уточнение формулировки, добавление примера, корректировка стоп-листа.


**MAJOR (+1.0)** — структурное изменение или рефакторинг, меняющее то, как модуль
работает или взаимодействует с другими (новый шаг алгоритма, новая обязательная проверка,
разбивка файла, изменение routing-логики).


Если изменение затрагивает несколько модулей одновременно — версия поднимается
в каждом затронутом файле независимо, с одной и той же датой в changelog для трассируемости.


**Как версия отражается физически — одна каноническая рабочая версия.**
Рабочий файл обновляется **на месте** с сохранением того же Drive file ID. Новые параллельные файлы `vN`, `old`, `backup`, `final-final` и аналогичные копии не создаются без отдельной команды Leo.


Номер версии может обновляться внутри файла и changelog. Legacy-суффикс версии в имени существующего файла не используется для выбора «самой новой» копии: источник истины — file ID и КАРТА СИСТЕМЫ. Координированное переименование допустимо только вместе с обновлением всех ссылок.


**Что делать со старой отдельной версией:** после проверки канонической версии удалить устаревшую рабочую копию.


**Исключение:** исторические оригиналы контента, revision-chain и доказательные материалы, где сама старая версия нужна для анализа. Такие объекты не являются рабочими дубликатами.


**Следствие для процесса:** перед изменением проверить КАРТУ СИСТЕМЫ и Drive file ID канонического файла. Не выбирать рабочий файл по максимальному номеру в имени. После изменения проверить отсутствие ненужных параллельных рабочих версий.

## ПОСТЭКСПЛУАТАЦИОННАЯ ПЕТЛЯ


Формализует переход от разового трения при реальном использовании модуля к точечной
правке файла. Без этого правила правки живут только внутри разговора и теряются
к следующей сессии — модуль наступает на то же самое снова.


**Сигналы, которые считаются трением:**
- Лео каждый раз перед хорошим результатом объясняет одно и то же уточнение,
  которого нет в блоке "Минимум данных" или в алгоритме модуля.
- Модуль выдумывает то, чего не должен (данные, факты, тон, деталь), и Лео каждый раз
  вычищает один и тот же тип лишнего вручную.


**Порог фиксации:** один случай — не повод трогать файл, может быть разовая аномалия
ввода. Два и более повторения одного и того же трения за использование модуля —
повод для точечной правки (Тип 1 из ТИПЫ ИЗМЕНЕНИЙ).


**Диагностика перед правкой:** если модуль выдумывает данные несмотря на явный запрет
("если данных нет — молчи, не додумывай") — не дублировать запрет ещё раз, это не решит
проблему. Это сигнал, что причина в другом месте: формулировка правила слишком общая,
нет конкретного примера "плохо/хорошо" под этот случай, либо правило перебивается
другим местом файла, у которого приоритет выше по факту, а не по замыслу. Диагностировать
по Шагу 1 общего процесса — причину, не симптом.


**Куда идёт правка, в зависимости от типа трения:**
- нехватка уточнения, которое Лео объясняет каждый раз → блок "Минимум данных",
  в блокирующие или неблокирующие пробелы
- выдумывание лишнего → блок "Анти-AI фильтр" / "Запрещено" + конкретный пример
  плохо/хорошо, не абстрактный запрет
- путаница в порядке или формате результата → блок "Алгоритм работы" или "Структура поста"


**Что не делать:** чинить трение только "на лету" в диалоге, не перенося правку в файл.
Разовое исправление в чате не долетает до следующей сессии.

## FEEDBACK LEARNING — НАКОПЛЕНИЕ РАЗБОРОВ BUDETSDELANO.AI


`Feedback-Learning-*` — третий, отдельный от ПОСТЭКСПЛУАТАЦИОННОЙ ПЕТЛИ и AUDIT механизм обучения.
Единственный допустимый источник новых CASE/PATTERN и подтверждений — содержательный разбор готового поста от budetsdelano.ai.
Разборы Critic, ChatGPT, Claude, других сервисов, ручные экспертные оценки и отдельные метрики могут использоваться
для текущей доработки, но не фиксируются в Feedback Learning.


**Цель:** не хранить обратную связь как архив, а возвращать проверенные рекомендации в следующие
релевантные посты.


**Механика:**
- каждый содержательный разбор budetsdelano.ai → CASE;
- обобщаемая рекомендация → PATTERN;
- 1 подтверждение → OBSERVATION;
- 2 → SIGNAL;
- 3+ → ACTIVE RULE CANDIDATE;
- явная команда Лео «больше никогда / всегда» может обойти порог.


**Важно:** CASE и PATTERN — данные обучения, не архитектурные правила. Когда паттерн достигает уровня
ACTIVE RULE CANDIDATE и требует изменения Router/модуля, это отдельная правка по ОБЯЗАТЕЛЬНОМУ
ПРОЦЕССУ. Так Feedback Learning не обходит версионирование и не переписывает модули автоматически.


**Автосохранение:** 16.08.2026 Лео уточнил постоянное разрешение: автоматически сохраняются только
содержательные разборы от budetsdelano.ai. Отдельного подтверждения для добавления такого CASE не требуется.
Любой другой источник обратной связи не создаёт CASE/PATTERN и не увеличивает счётчики подтверждений.
Если запись требует архитектурного изменения — подтверждение требуется по обычным правилам META, кроме
случаев явной команды на конкретную правку.


**Перед Facebook-генерацией:** Router обязан загрузить актуальный Feedback Learning и выбрать только
релевантные паттерны. Приоритет: факты → модуль → Router → Feedback Learning.


**Версионирование журнала:** новый CASE или изменение счётчиков PATTERN = MINOR-версия
`Feedback-Learning` (+0.1). Изменение самой схемы обучения = MAJOR.


**Связь трёх механизмов:**


| | ПОСТЭКСПЛУАТАЦИОННАЯ ПЕТЛЯ | AUDIT | FEEDBACK LEARNING |
|---|---|---|---|
| Материал | повторяющееся трение, которое Лео описывает в работе | Session Log отдельных внешних проверок Critic, если Leo их запускал | разборы готовых постов от budetsdelano.ai |
| Основная задача | чинить повторяющийся рабочий баг | кластеризовать ошибки Critic | накапливать то, что повышает качество/реакцию аудитории |
| Порог | 2+ повторения | 3+ для предложения постоянного правила | 1 OBSERVATION / 2 SIGNAL / 3+ ACTIVE RULE CANDIDATE |
| Результат | точечная правка модуля | предложение правила в стоп-лист | релевантный паттерн для генерации; при 3+ — кандидат на системное правило |

## AUDIT — ПРОТОКОЛ САМООБУЧЕНИЯ СИСТЕМЫ (Audit-v1.2.md)


Отдельный механизм от ПОСТЭКСПЛУАТАЦИОННОЙ ПЕТЛИ выше — работает на другом материале,
с другим порогом, но приводит к тому же типу результата.


**Что делает:** когда Leo отдельно запускает Critic и завершается внешний цикл оценки/правок с финальным вердиктом ✅, Critic может сохранить Session Log отдельным файлом в папку
Session-Logs (`1BNm2cqji3XtWd5R6Ww6Crvbg76POhilq`), без участия Лео. Периодически —
по команде Лео ("запусти аудит ошибок"), ориентир раз в месяц или 15-20 накопленных
файлов — запускается аудит: все Session Log читаются, ошибки кластеризуются по смысловому
паттерну (не по дословному совпадению), и при 3+ повторениях одного паттерна предлагается
постоянное правило в стоп-лист соответствующего модуля.


**Отличие от ПОСТЭКСПЛУАТАЦИОННОЙ ПЕТЛИ:**


| | ПОСТЭКСПЛУАТАЦИОННАЯ ПЕТЛЯ | AUDIT |
|---|---|---|
| Материал | трение, которое Лео описывает прямо в этом чате | Session Log из отдельно запущенных Leo внешних проверок Critic |
| Порог | 2+ повторения | 1 — зафиксировать без действия; 2 — наблюдение; 3+ — предложить правило |
| Запуск | по факту трения, в моменте | по команде Лео, периодически |
| Кто выполняет | Claude в этом дев-чате | Critic сохраняет лог только в рамках отдельно запущенной Leo проверки; Claude здесь кластеризует по команде |


Оба механизма сходятся в одной точке: точечная правка стоп-листа модуля (Тип 1 из
ТИПЫ ИЗМЕНЕНИЙ), которая проходит через тот же ОБЯЗАТЕЛЬНЫЙ ПРОЦЕСС и ВЕРСИОНИРОВАНИЕ.
Не дублировать анализ — если трение уже пойманное вручную в диалоге совпадает с тем,
что покажет следующий Audit, это не два разных изменения, а одно.


**Немедленное правило в обход порога:** если Лео говорит "больше никогда так не пиши" —
правка вносится сразу в файл модуля, без ожидания 3+ повторений и без ожидания
периодического Audit.


**Границы метода:** не меняет веса модели — это не настоящее дообучение, а дистилляция
повторяющихся ошибок в правила стоп-листа. Не синхронизирует ChatGPT и Drive автоматически —

## External Library Governance — Archivarius + YouMind
Archivarius подключается через `ARCHIVARIUS_RUNTIME_BRIDGE.md`, `ARCHIVARIUS_RUNTIME_TRUSTED.md` и `ARCHIVARIUS_RUNTIME_BLOCKLIST.md`.
